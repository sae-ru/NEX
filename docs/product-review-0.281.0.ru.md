# NEX для разработки с LLM. Оценка и план работ

Срез на 22 ноября 2026 года, [main 26e78f53](https://github.com/sae-ru/NEX/tree/26e78f53), инструмент 0.281.0, язык новых проектов 0.30. Этот документ предлагает порядок работ. Приёмку каждой задачи предстоит провести.

**Решение.** Я бы выбрал NEX для пилота внутреннего приложения с типизированной моделью, небольшим HTTP API, SQLite и браузерным клиентом. Я бы сохранил существующие крупные Java/Python-системы и подключал к ним отдельный модуль NEX там, где есть измеримая причина. Массовый перенос сегодня увеличил бы риск и стоимость сопровождения. Главная ставка проекта — передать модели ровно столько сведений о программе, чтобы она с первой или второй попытки внесла проверяемое изменение.

## Что уже помогает писать программы

- Типы, эффекты и разделение client/server/shared позволяют компилятору обнаружить целый класс ошибок до запуска. Установка SDK, нативная производительность и расход модели при разработке — три разных результата, каждый требует своего измерения.
- Семантический граф находит определение, вызываемые функции и зависимости. В небольшом проекте ответ о функции main занял 844 байта. Полный ответ describe того же инструмента — 237 550 байт. Байты здесь характеризуют выдачу CLI. Токены зависят от модели и содержимого запроса.
- [Workboard](../examples/workboard/README.md) связывает модель, браузерный Worker, HTTP, SQLite и файловое восстановление. В отдельной копии я переименовал поле Summary.characters в scalar_count. Проверка за 0,06 с указала на оставшееся обращение в client.nex:63. После исправления клиент и сервер прошли check, а тест клиента для web занял 0,68 с. Это один опыт на Mac с локальной сборкой. Он не измеряет время рассуждения модели, внешний wire-контракт, браузерный UI или выпуск обновления.
- В другом небольшом проекте ошибка на границе цикла прошла проверку типов, а тест за 0,04 с указал строку assert и идентификатор операции. После исправления тест с нативным исполнением прошёл за 1,66 с. На таком сбое мне как автору полезнее сразу увидеть имя теста, ожидаемое и полученное значения, чем читать общий справочник.
- Ручной порт [очереди Apache](migration-readiness.md) сравнивали с оригинальным Java по 995 наблюдениям, включая нативные сборки, интерпретатор и TypeScript. Это подходящий способ принять отдельный перенесённый компонент.
- Историческое измерение инкрементальной сборки на 10 000 объявлений особенно показательно. После правки одной функции компилировалась одна из 9 900 достижимых, но команда всё равно заняла 84,38 с. Для разработчика важна задержка до результата. Следует отдельно измерить чтение графа, проверку, генерацию и линковку в актуальном SDK. [Условия измерения](overview.en.md#measurements)

## Что известно о цене

[Одна кампания](llm-cost-qwen38-27b-2026-11-17.ru.md) использовала Qwen3.8 27B, SDK-исходники 0.280.1 и язык 0.30. Десять небольших задач, по два детерминированных повтора на язык. В таблице весь известный расход и всё время попыток, включая неудачные, разделены на число принятых решений. Время округлено. [Первичные числа](evidence/llm-qwen38-27b-0.280.1-2026-11-17.json)

| Язык | Принято | Известные токены на принятое решение | Время всех попыток на принятое решение |
|---|---:|---:|---:|
| NEX | 6/20 | ≥148 454 | 4 мин 45 с |
| C++ | 18/20 | ≈15 471 | 1 мин 37 с |
| Python | 20/20 | ≈6 446 | 40 с |

У двух вызовов NEX отсутствует usage, денежная цена и доля кэшированного входа неизвестны. Из известных 890 724 токенов NEX 880 230 были входными. Полная история возвращалась модели на следующих шагах. Её вклад в разницу предстоит установить сравнением двух вариантов на одинаковых задачах. Два решения про Unicode отклонил модельный ревьюер, хотя исполняемые проверки прошли и спецификация подтверждала индексацию по Unicode scalar. [Позднейший пилот](llm-entry-v3.md) исправил часть проблем протокола и дал принятые результаты всех трёх языков на одной задаче. Воспроизводимого сравнения конкретной модели Codex на сопровождении приложений пока нет.

## План заданий

| Приоритет | Работа | Когда можно закрыть |
|---|---|---|
| P0. Исходная точка | На зафиксированном SDK расширить существующий протокол и nex cost. Отдельно измерять новую функцию, ремонт дефекта, межмодульную правку и эксплуатацию. Использовать задачи Workboard и независимый незнакомый модели проект. | Для каждого языка одна модель, эквивалентный стартовый код и контракт, одинаковые права и бюджет, независимые свежие сессии, скрытые случаи. Сохранены все попытки. Известны доля принятых и принятых с первого раза, время, токены, число вызовов и вмешательств человека. |
| P0. Сведения для модели | Согласовать quickstart, llms.txt и системный промпт с поставляемым SDK. Собрать компактный ответ поверх context, subgraph, explain и help. Отдавать участок исходника, затронутые сигнатуры и эффекты, диагностику и ближайший тест. Справку переиспользовать по версии, языку и хешу дескриптора, сведения о коде — по ревизии и точному хешу источника. | На одной модели и одном SDK сравнить существующую и компактную выдачу. Сократились входные токены и время на принятый ремонт, доля принятых и результаты скрытых тестов сохранились. Проверить переход между версиями, устаревшую ревизию и незакоммиченный текст. |
| P0. Исправление | Связать диагностику с существующими test --symbol и fix. Для сравнений внутри assert показывать тест, выражение и краткие значения операндов, когда это возможно без повторного вычисления. Значения ограничить по размеру, предусмотреть сокрытие чувствительных данных. Для изменений wire-схемы отдельно предлагать тест совместимости данных. | На ошибках границы, типа, эффекта и изменения API измерена доля ремонтов за одну правку. Тест с побочным эффектом подтверждает однократное вычисление. При неполном анализе зависимостей инструмент сообщает, какую более широкую проверку запустить. |
| P1. Качество продукта | Задать контрольный Workboard-сценарий с одновременными запросами, Unicode, отменой, перезапуском и чтением прежних данных. Использовать существующие инструменты замеров. Зафиксировать доверенные границы SDK, FFI и провайдеров, предоставлять только требуемые ресурсы. | Заранее зафиксированы машина, данные, нагрузка, допустимые p95, пиковая память и ожидания по сохранности данных. Для подтверждённых записей, отказа в доступе и отмены есть явный контракт; восстановление повторяемо. Для каждой поставляемой реализации проверяется одинаковый наблюдаемый результат в применимых режимах. |
| P1. Поставка SDK | В одном месте связать версию языка проекта, версию SDK, исходный коммит, доступный архив, checksum и успешный отчёт именно этого архива. Пройти путь пользователя без дерева исходников на каждой заявленной ОС. | Новый пользователь устанавливает архив, создаёт проект 0.30, исправляет ошибку, собирает и запускает приложение. Сохранены результаты обновления с беты, восстановления прежнего проекта и ограничения платформы. |
| P2. Решение о расширении | Повторить сравнение на удержанном наборе задач и второй модели, например доступной через Codex. Отдельно измерить создание и сопровождение. Для собственной инфраструктуры учесть время машины, работу оператора и CI, для платного провайдера — подтверждённые списания, где доступны. | Публикуется результат по каждой модели и классу задач с долей успеха, временем, стоимостью и неизвестными полями. Ориентир проекта для заявления об экономии — 30% меньше токенов относительно C++ при не худшей успешности. Для Python сравнение отдельное. |

Короткую проверку затронутого поведения выполнять во время разработки. Полный прогон платформ и проверку установленного архива привязывать к завершённому этапу и релизному кандидату. Краткую сводку о цене дополнять холодной и тёплой сборкой, размером поставки и расходом ресурсов работающего приложения. Для малых выборок показывать индивидуальные результаты.

**Оставить в ядре** типы, эффекты, проверяемые ошибки, области жизни задач, контракты, историю и воспроизводимость сборки. Стандартные коллекции, рецепты работы с JSON и SQLite и проверенные примеры полезнее дополнительных вариантов синтаксиса. Вернуть в активный план Studio, массовые конвертеры и универсальный GPU/NPU, когда появится конкретный пользовательский сценарий с измеримым выигрышем. До того использовать уже проверенные провайдеры там, где они решают задачу.

Для решения о 1.0 применять [контракт совместимости](compatibility.md). Для решения о переносе действующего продукта нужны отдельно подтверждённая экономика сопровождения и качество самого приложения. Уже опубликованный [SDK 0.280.1](https://github.com/sae-ru/NEX/releases/tag/v0.280.1) — предварительный пакет для macOS ARM64, а 0.281.0 — версия изученных исходников.
