# Критерии качества NEX

NEX — Neural Execution Language. Цель — надёжно разрабатывать крупные системы
с производительностью нативного кода, простым рабочим процессом и меньшими
затратами LLM на получение **проверенного изменения**. Компактность синтаксиса
сама по себе не доказывает качество или экономию. Сейчас NEX ещё не достиг
зрелости C++ или Python; этот документ задаёт требования, а не заявляет паритет.

## Что должно быть готово

| Область | Критерий приёмки |
| --- | --- |
| Корректность | Одинаковые наблюдаемые результаты и проверяемые ошибки в native, TypeScript и интерпретаторе; отрицательные тесты для запрещённых программ. |
| Ошибки | Типизированные ожидаемые ошибки, удобная передача между слоями, контекст причины и стека; явные границы перехвата и освобождение ресурсов при каждом выходе. Отмена и лимиты не должны незаметно поглощаться. |
| Память | Ясные правила владения и неизменяемых значений; очистка при возврате, ошибке и отмене; отсутствие выявленных утечек, UB и гонок в заявленных проверках. |
| Многопоточность | Операции доступны из NEX, проверены эффекты и захваты; задачи завершаются вместе с областью, делят отмену/лимиты и не умножают потоки без ограничения. |
| Крупные проекты | Модули, библиотеки, проверяемые интерфейсы, воспроизводимые зависимости, инкрементальная сборка и изменения нескольких компонентов без потери архитектуры. |
| Инструменты | Установка, диагностика, тесты, debugger, profiler, Git/граф и обновление проекта образуют проверенный полный цикл. |
| Платформы | Сборка и выполнение проверены отдельно для каждой заявленной ОС/архитектуры; CPU/GPU/NPU проверяются на реальном устройстве с явным выбором исполнителя. |
| LLM | Разные модели используют одну версионную спецификацию, небольшие целевые контексты и одни критерии приёмки. Успех проверяет инструмент, а не уверенность модели. |

В языке 0.17 есть `result<T>`, передача ожидаемой ошибки оператором `?`
и завершающие checked traps; `try/catch/throw` ещё нет. Реализация `?` согласована
в checker/interpreter/native/TypeScript; полная приёмка текущей поставки и оценка
удобства модели ошибок продолжаются. Кандидат 0.18 подключает ordered CPU map к исходному языку и проверяет типы,
эффекты, realm и actual captures. Native использует CPU threads; reference и
текущий TypeScript исполняются последовательно. Полная приёмка и асинхронные
browser workers/общие задачи остаются обязательными. Новые source-возможности требуют явной версии и миграции
с сохранением истории. Команды discovery не меняют язык.

## Проверяемые сценарии первой стабильной версии

1. Создать библиотеку обработки данных, подключить её к CLI и HTTP-сервису;
   изменить общий тип и обновить потребителей через checked интерфейсы.
2. Изменить серверное поведение и соответствующую веб-модель, сохранив границы
   client/shared/server, авторизацию и транзакции.
3. Найти и исправить ошибку по диагностике, stopped frame и профилю; проверить
   корректность, память и повторное выполнение принятого task-контракта.
4. Выполнить CPU-задачу параллельно, отменить её и обработать ошибку дочерней
   задачи без гонок, оставшихся потоков и потерянных ресурсов.
5. Проверить сгенерированный проект из100 модулей/10,000 функций, затем изменить
   один модуль. Измерить проверку, сборку, объём перечитанного контекста и память.
   Frontend, интерпретатор, сохранение всех 10 000 идентификаторов и ограниченный
   контекст уже проверены в изолированном запуске 0.89; полная нативная сборка,
   её повторное использование и итоговая приёмка масштаба остаются открытыми.

Для каждого сценария сохраняются исходники и их хеши, компиляторы, зависимости,
команды, оборудование, ОС, критерии и полные результаты. Пропуски и недоступные
возможности считаются незавершённой проверкой, а не успехом.

## Сравнение производительности и удобства

Сравниваем NEX с зафиксированными реализациями C++ и Python на одинаковых
входах и алгоритмах с одинаковыми требованиями к ошибкам, Unicode и безопасности.
Для native фиксируем профиль, оптимизации и зависимости. Считаем время сборки
отдельно от запуска; измеряем пропускную способность, p50/p95/p99, RSS и размер
поставки. Изменение алгоритма или более слабые проверки не считаются выигрышем
языка. Результат одного CPU/сервера не переносится на все платформы.

Начальная цель для выбранных CPU-ядер — не более20% потери пропускной
способности относительно согласованного C++ baseline. Для прикладных задач
измеряем также скорость безопасного изменения относительно Python. Это
проектная цель; обещания одинаковой скорости для любых программ нет.

## Как считать стоимость LLM

Основная метрика — **все токены на одну принятую задачу**, а не длина файла.
Учитываем system/task prompt, документацию, контекст, ответы инструментов,
генерацию, ошибочные попытки и исправления. Отдельно сохраняем cached/uncached
input, output, фактическое время, число обращений и подтверждённую стоимость.
Цены и tokenizer/model IDs берём из конкретного запуска, не подставляем оценки.

Один набор задач выполняется для NEX, C++ и Python одной и той же моделью с
одинаковыми правами, бюджетом, критериями и доступом к инструментам. Затем
повторяется как минимум с тремя независимо выбранными моделями и несколькими
повторами. Сохраняются неудачные задачи; считаем успешность, медиану и хвост
затрат, а не выбираем лучший ответ. Затраты на failed runs также учитываются.

Начальная цель — минимум30% меньше совокупных токенов относительно C++ на
согласованном наборе задач без ухудшения успешности. С Python сравнение ведётся
отдельно; универсальная экономия заранее не объявляется. Размер JSON в байтах,
число строк и приблизительные токены не заменяют реальные tokenizer/usage данные.

## Порядок работы

- Завершить воспроизводимую поставку и исправить найденные отказы приёмки.
- Снизить обязательный контекст: краткое discovery, разделы по запросу,
  ограниченный графовый контекст и небольшие проверяемые правки.
- Завершить модель ошибок и source concurrency вместе со всеми backend'ами.
- Проверить масштаб проекта, производительность и полный цикл разработки.
- Провести сравнение нескольких LLM и опубликовать результат вместе с провалами.

Отдельная [проверка native100x10000 в094](evidence/native-scale-0.94.0.json)
подтверждает cold9,900/warm0/edit1 и обе архивные ревизии после удаления исходных
путей проекта. Повторная сборка всё ещё заняла81с; текущий095 отдельно ускоряет
планирование, а полная его проверка продолжается. Это не измерение стоимости LLM.

У [первого checked-core сравнения](evidence/checked-core-0.94.0.json) есть
[воспроизводимый opt-in runner](../experiments/quality/README.md).100миллионов
шагов одного положительного целочисленного алгоритма дали медианы0.307272с NEX,
0.292982с checked C++ и9.922024с CPython3.9.6, по пять повторов на MacARM64.
На том же компьютере шли другие проверки; C++ baseline не включает runtime
отмены/лимитов. Эти наблюдения не доказывают общий паритет или экономию токенов.

Полные требования остаются в `PLAN.md`; реализованные возможности сообщает
конкретный `nex describe`, а доказательства относятся к указанному compiler/source
cohort. Номер версии, работающий пример или большое количество тестов сами по
себе не означают, что язык уже соответствует этим критериям.
