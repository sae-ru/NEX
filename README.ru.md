# NEX — Neural Execution Language

**Язык нейронного исполнения.**

[English](README.md) · [Описание языка](docs/overview.ru.md) · [Начать работу](docs/getting-started.ru.md) · [Материалы для LLM](llm/LEARNING.md)

Главная идея NEX — передавать максимум точного смысла минимальным необходимым
числом токенов, сохраняя высокую производительность и безопасность исполнения.
Это цели проекта с проверяемыми критериями готовности.

NEX — язык и инструменты разработки для людей и языковых моделей. Вы пишете
читаемые исходники `.nex`. Компилятор проверяет типы, эффекты и границы исполнения,
хранит версионный семантический граф и генерирует нативный код через MLIR/LLVM
либо TypeScript для браузера. Готовая программа работает самостоятельно: LLM
при её исполнении не требуется.

```nex
module hello;
fn answer(x: i64) -> i64 { return x * 2; }
fn main() -> unit !{io} { print(answer(21)); }
test fn answer_is_42() -> unit { assert(answer(21) == 42); }
```

## За счёт чего ускоряется работа

- **Меньше повторного контекста.** Модель получает нужную возможность компилятора
  или ограниченный контекст символа вместо всего проекта.
- **Ошибки обнаруживаются раньше.** Проверки типов, эффектов и realms дают
  диагностику до исполнения. Тесты сравнивают поведение разных способов исполнения.
- **Меньше повторной компиляции.** Идентичность содержимого и кэш позволяют
  повторно использовать неизменённые нативные функции и объекты среды исполнения.
- **Нативное исполнение.** Приложение выполняет машинный код. Параллельные CPU-
  операции и провайдеры устройств имеют явно описанные границы проверки.

[Измерения и ограничения](docs/overview.ru.md#измерения) приведены отдельно.
[Свежий целочисленный benchmark 0.162.2](docs/evidence/macos-e63-sdk-complete-0.162.2-2026-11-09.json)
дал медианы 0,296170 с для NEX, 0,290189 с для проверяемого C++ и 7,610111 с для Python
на одном Mac. Это измерение одного алгоритма. Полная экономия токенов
на принятых задачах разных LLM пока не измерена.

## Что можно разрабатывать

Реализованы модули, обобщения и трейты, неизменяемые агрегаты, Unicode-строки и
байты, проверяемая арифметика, типизированные ошибки и `finally`, структурированные
задачи, история графа, компоненты проектов, нативные библиотеки, HTTP/API и
браузерные адаптеры, отладка, профилирование и ограниченная скалярная верификация.

Один проект может разделять переносимую логику между нативным сервером и
TypeScript / React / Vite клиентом. Устройства подключаются явными доверенными
провайдерами. [Подробное описание](docs/overview.ru.md) разделяет возможности
языка и фактически проверенные платформы.

## Сборка и использование

Начните с [актуальной инструкции](docs/getting-started.ru.md). Для сборки из
исходников нужны C++20, CMake 3.25+, LLVM/MLIR 22.1.x, SQLite, OpenSSL 3, Z3 и
Python 3.10+. Полный CTest включает веб/TypeScript: для него нужны также
Node.js 22.18+, npm и закреплённые lock-файлом зависимости.
В Unix ELF-проверкам нужны также `ld.lld` и `llvm-ar` из LLVM22.1. При отдельной
установке LLD задайте `-DNEX_ELF_TEST_LD=/абсолютный/путь/к/ld.lld`.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j 4
npm --prefix web ci --cache "$PWD/build/npm-cache" --ignore-scripts --no-audit --no-fund
NEX_TSC="$PWD/web/node_modules/typescript/bin/tsc" \
NEX_NPM_CACHE="$PWD/build/npm-cache" \
ctest --test-dir build --output-on-failure
cmake --install build --prefix /absolute/path/to/nex-sdk
```

Сохранённые результаты CTest проверяет [сверка реестра и JUnit](docs/ctest-results.md).
Она учитывает обязательные подготовительные группы и отклоняет неполные
прогоны и пропуски групп.

Каталоги `bin/nex` и `share/nex` должны оставаться вместе. Обычная установка
CMake использует зависимости компьютера сборки; [переносимый SDK](docs/sdk.md)
упаковывается и проверяется отдельно.

```sh
nex doctor --json
nex describe --kind index --json
nex init /path/to/my-app
```
