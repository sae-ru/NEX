# NEX — Neural Execution Language

[Краткий актуальный статус](docs/STATUS.current.md) · [Приоритеты улучшений](docs/development-priorities.md)
**Язык нейронного исполнения.**

[English](README.md) · [Описание языка](docs/overview.ru.md) · [Начать работу](docs/getting-started.ru.md) · [Материалы для LLM](llm/LEARNING.md)

Главная идея NEX — передавать максимум точного смысла минимальным необходимым
числом токенов, сохраняя высокую производительность и безопасность исполнения.
Это цели проекта с проверяемыми критериями готовности.

NEX — язык и инструменты разработки для людей и языковых моделей. Вы пишете
читаемые исходники `.nex`. Компилятор проверяет типы, эффекты и границы исполнения,
хранит версионный семантический граф и генерирует нативный код через MLIR/LLVM
либо TypeScript для браузера. Готовая программа работает самостоятельно: LLM
при её исполнении не требуется.

```nex
module hello;
fn answer(x: i64) -> i64 { return x * 2; }
fn main() -> unit !{io} { print(answer(21)); }
test fn answer_is_42() -> unit { assert(answer(21) == 42); }
```

## За счёт чего ускоряется работа

- **Меньше повторного контекста.** Модель получает нужную возможность компилятора
  или ограниченный контекст символа вместо всего проекта.
- **Ошибки обнаруживаются раньше.** Проверки типов, эффектов и realms дают
  диагностику до исполнения. Тесты сравнивают поведение разных способов исполнения.
- **Меньше повторной компиляции.** Идентичность содержимого и кэш позволяют
  повторно использовать неизменённые нативные функции и объекты среды исполнения.
- **Нативное исполнение.** Приложение выполняет машинный код. Параллельные CPU-
  операции и провайдеры устройств имеют явно описанные границы проверки.

[Измерения и ограничения](docs/overview.ru.md#измерения) приведены отдельно.
[Зафиксированный целочисленный benchmark 0.162.2](docs/evidence/macos-e63-sdk-complete-0.162.2-2026-11-09.json)
дал медианы 0,296170 с для NEX, 0,290189 с для проверяемого C++ и 7,610111 с для Python
на одном Mac. Это измерение одного алгоритма. [Первый замер локальной Qwen3.8 27B](docs/llm-cost-qwen38-27b-2026-11-11.ru.md)
не подтвердил экономию токенов NEX; другие модели/задачи не измерялись.

## Что можно разрабатывать

Реализованы модули, обобщения и трейты, неизменяемые агрегаты, линейное
построение list/text/bytes, Unicode-строки и байты, проверяемая арифметика,
типизированные ошибки и `finally`, структурированные задачи, история графа,
компоненты проектов, нативные библиотеки, HTTP/API и браузерные адаптеры,
отладка, профилирование и ограниченная скалярная верификация.

Один проект может разделять переносимую логику между нативным сервером и
TypeScript / React / Vite клиентом. Устройства подключаются явными доверенными
провайдерами. [Подробное описание](docs/overview.ru.md) разделяет возможности
языка и фактически проверенные платформы.

## Состояние разработки

Текущие исходники: **toolchain 0.207.0 / язык 0.28 / task ABI 7**, в разработке.
Сообщения фатальных ошибок сохраняют NUL и Unicode при передаче через исходный
код, задачи и диагностику frontend; ограничения структурированных журналов
сохраняются. [Результаты этого блока](docs/evidence/runtime-diagnostic-text-0.165.0-2026-11-10.json).
CUDA также форматирует конечные f64 и поддерживаемые составные значения с явной
ёмкостью строки; [область реализации и проверки](docs/evidence/cuda-formatting-0.165.0-2026-11-10.json).
[Стандартная библиотека](docs/stdlib.md) расширена: Unicode split/replace/trim,
функции списков/стабильная сортировка и checked integer math. Стоимость
копирования описана явно; линейные построители остаются в плане.
Текущий [форматтер исходников](docs/formatting.md): `nex fmt FILE` показывает результат,
`--check` проверяет стиль без записи, `--write` меняет выбранный файл. Комментарии
и написание литералов сохраняются; граф и миграция не открываются.
[Справка CLI](docs/cli.md) теперь доступна для отдельной команды; добавлены
автодополнение и `--quiet` для служебных успешных сообщений с сохранением
JSON, результатов, ошибок и вывода программы.
[Конструктор списков](docs/list-construction.md) строит результат одним буфером,
выводит эффекты callbacks и использует обычные исключения/задачи. Map/filter/
reverse и слияние сортировки переведены на этот путь; замеры скорости и полная
платформенная приёмка остаются отдельными этапами.
[Учебный корпус0.28](llm/corpus.json) теперь содержит9 проверенных проектов и6
контрпримеров с наблюдениями reference/native Release/TypeScript.
[Воспроизводимый workflow](docs/learning-corpus.md) проверяет и общие capability-
контракты; учебные примеры и реальный замер моделей имеют разные критерии.
Полная приёмка соответствующего переносимого SDK ещё не завершена. Возможности
исходников, аппаратные проверки и переносимая поставка имеют отдельные результаты.
[`nex cost`](experiments/quality/llm_cost.md) считает затраты по сохранённым
данным испытаний. Подготовлены протокол и10 контрактов задач NEX/C++/Python;
приёмка проверена30 эталонными решениями и30 неправильными стартами.
Локальный сборщик Qwen, ограниченные инструменты и учёт отдельного source review реализованы.
[Основной замер60 попыток Qwen завершён](docs/llm-cost-qwen38-27b-2026-11-11.ru.md):
принято4/20 NEX,14/20 C++ и20/20 Python. Экономии токенов NEX нет;
первоначальные отказы и старые пилоты сохранены отдельно.
[Краткий языковой вход](docs/diagnostics.md) добавляет `nex guide --kind quick`
и встроенные объяснения `nex explain CODE` с проверенными примерами. Новая
экономия токенов ещё не измерялась. [Слой core из12 групп](docs/testing.md)
добавляет диагностики к прежнему11-групповому baseline; полная приёмка остаётся отдельным этапом.
[CI](docs/ci.md) описывает macOS/Linux core и отдельный Linux full;
облачные задания пока не выполнялись.

Прежний [базовый macOS SDK `61fbd21`](docs/evidence/macos-baseline-SDK-82-184-0.165.0-2026-11-10.json)
прошёл 82 поддерживаемые фазы, 184 дополнительных случая и 4000 вызовов C++ с

Его последующие этапы и более поздний SDK с новыми публичными инструментами Metal
сохраняют отдельные проверки.

Компилятор также поддерживает `nex emit --kind cuda`: обычные чистые функции
`i64`/`f64`/`bool`/`unit`, структуры, enum, `result`, вложенный `match` и контракты
превращаются в CUDA C++20. Поддержаны неизменяемые списки и `bytes` с явной ёмкостью
GPU, динамический UTF-8 через `--text-capacity`, проверяемый `as_i64` и распространение обычной ошибки через `?`. [Описание CUDA](docs/gpu-codegen.md#cuda-source-emission) содержит
формат конечных binary64, карты исходников и подготовку явного провайдера.
Генерация кода не даёт доступа к устройству; аппаратная приёмка текущего
провайдера и SDK ещё предстоит.

[Скалярный Metal-backend](docs/gpu-codegen.md) генерирует достижимые общие чистые
функции `i64`/`bool`/`unit` из проверенного AST. Его явный провайдер owned-задач
экспериментальный; SDK устанавливает инструменты подготовки и описывает их в
`gpu_codegen.owned_provider`. Пошаговая отладка и профилирование GPU, более общая
GPU/NPU-компиляция, Apple NPU, полный мобильный/native UI, NEX Studio, конвертер
проектов и измеренная полная экономия токенов разных LLM остаются в [плане](PLAN.md).

Отдельный [набор CUDA из проверенного AST](docs/evidence/windows-checked-AST-CUDA-physical-0.165.0-2026-11-10.json)
прошёл32 сгенерированных ядра/186 результатов на RTX3090 с реальным NVRTC12.1.
Санитайзер не подключился до начала GPU-работы; аппаратная приёмка f64 и нового
owned-провайдера CUDA ещё предстоит.

[STATUS.md](STATUS.md) и [версионные результаты](docs/evidence/) сохраняют

## Сборка и использование

Начните с [актуальной инструкции](docs/getting-started.ru.md). Для сборки из
исходников нужны C++20, CMake 3.25+, LLVM/MLIR 22.1.x или 23.1.x, SQLite, OpenSSL 3 или 4, Z3 и
Python 3.10+. Полный CTest включает веб/TypeScript: для него нужны также
Node.js 22.18+, npm и закреплённые lock-файлом зависимости.
В Unix ELF-проверкам нужны также `ld.lld` и `llvm-ar` из выбранного LLVM22.1/23.1. При отдельной
установке LLD задайте `-DNEX_ELF_TEST_LD=/абсолютный/путь/к/ld.lld`.

После конфигурации для короткого цикла разработки есть [слой core из11 групп](docs/testing.md):

```sh
cmake --build build --target nex_core_tests -j 4
ctest --test-dir build -L '^core$' --output-on-failure
```

Ему нужны собранный компилятор и Python. Веб-зависимости не требуются.
Метки также выделяют browser/platform/sdk/scale.

[Пресеты разработки](docs/development-build.md) также дают одну команду
`cmake --workflow --preset dev-core` с отдельными каталогами Debug/Release.
Проверка отчётов и границы автоматизации описаны в [руководстве CI](docs/ci.md).
[Команда сборки SDK](docs/sdk-build.md) объединяет существующие macOS/Linux
workflow; полный прогон новой команды ещё предстоит.

Полный цикл для согласованного этапа приёмки:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j 4
npm --prefix web ci --cache "$PWD/build/npm-cache" --ignore-scripts --no-audit --no-fund
NEX_TSC="$PWD/web/node_modules/typescript/bin/tsc" \
NEX_NPM_CACHE="$PWD/build/npm-cache" \
ctest --test-dir build --output-on-failure
cmake --install build --prefix /absolute/path/to/nex-sdk
```

Сохранённые результаты CTest проверяет [сверка реестра и JUnit](docs/ctest-results.md).
Она учитывает обязательные подготовительные группы и отклоняет неполные
прогоны и пропуски групп.

Каталоги `bin/nex` и `share/nex` должны оставаться вместе. Обычная установка
CMake использует зависимости компьютера сборки; [переносимый SDK](docs/sdk.md)
упаковывается и проверяется отдельно.

```sh
nex doctor --json
nex describe --kind index --json
nex init /path/to/my-app
```
